# 001 — Opus 5.5 설계 리뷰 루프는 라운드가 늘수록 희귀 엣지케이스로 수렴한다

- **날짜:** 2026-10-11
- **관련 작업:** `commit-push` 스킬(.claude/skills/commit-push/SKILL.md) 설계

## 무슨 일이 있었는가

CLAUDE.md의 필수 절차 3단계(설계 리뷰)를 그대로 적용해, git commit/push를 Haiku 5.5에
위임하는 스킬 설계를 Opus 5.5로 반복 리뷰했다. 4라운드 연속 REJECT가 나왔는데, 라운드가
진행될수록 지적 사항의 실질적 위험도가 급격히 낮아졌다:

- 1~2라운드: 승인 전 커밋되는 구조적 결함, 검증 누락 — 실제로 중요한 문제.
- 3라운드: `git fetch` 누락, 메시지 비교 방식의 shell-injection 위험 — 여전히 실질적.
- 4라운드: fork용 `pushRemote`/`remote.pushDefault` 해석, 커밋 0개인 리포(root commit)
  케이스, `git log --format=%B`의 trailing newline 등 — home-cctv는 origin 하나뿐인 단일
  clone이고 이미 커밋이 있는 리포라 **실제로는 발생할 수 없는** 케이스였다.

## 왜 그랬는가

Opus 5.5는 "이 설계가 일반적인 git 사용 환경 전체에서 안전한가"를 기준으로 리뷰했기 때문에,
라운드가 반복될수록 이 리포의 실제 제약(단일 origin, 단일 브랜치, 이미 커밋 존재)과 무관한
이론적 엣지케이스까지 파고들었다. 설계 리뷰 단계에는 "이 리포/이 사용 맥락에서 실제로 일어날
수 있는가"라는 범위 제한이 빠져 있었다.

## 다음에는 어떻게 할 것인가

- 설계를 Opus 5.5에 넘길 때, 리뷰 범위를 "이 리포의 실제 git 구성(origin 하나, 커밋 존재,
  단일 로컬 clone)"으로 명시적으로 한정해 전달한다. 범용 안전성이 아니라 이 맥락에서의
  안전성을 묻는다.
- 반려가 3라운드를 넘기고 지적 사항이 "이 환경에서는 발생 안 함"으로 방어 가능해지면, 추가
  반복 대신 사용자에게 "계속 반복 vs 지금 설계로 확정"을 물어본다 (실제로 이번엔 그렇게 했고
  사용자가 확정을 선택함). 이 판단을 CLAUDE.md의 3단계 설명에 "단, 반려 이유가 이 리포의
  실제 사용 환경에서 발생 불가능한 경우로 수렴하면 설계에 그 사실을 문서화하고 사용자 확인을
  받아 종료할 수 있다"로 보강하는 것을 고려할 것.
